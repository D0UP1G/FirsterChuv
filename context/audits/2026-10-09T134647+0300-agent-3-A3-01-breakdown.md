## Сверка с кейсом

Исходный кейс требует реальный запуск решений без fake verdict, отдельный изолированный контейнер на запуск, лимиты времени/памяти/числа процессов и отсутствие сети, доступа к host filesystem и секретам (стр. 4, 7). Он указывает, что организаторы предоставляют общий пакет задач, формат которого описан в README (стр. 4). Это соответствует `J01`, `J03`, `S01`, `D06` и будущей проверке `T18`.

Функциональная проверка на официальном пакете не выполнена. Smoke-задача может подтвердить только механизм и не заменяет официальный пакет/README, как явно указано в roadmap и `mvp-acceptance.md`.

## Решения и отклонения

- Используется `feature/sandbox-proof` от актуального `origin/develop`, как требует GitFlow.
- Текущая задача ограничена A3-01; agent 1 владеет платформой/общей интеграцией, agent 2 — матчем/events. Их изменения не трогаются.
- Из-за отсутствия пакета и Engine окончательное доказательство A3-01 нельзя объявлять выполненным. Продолжать автономную подготовку smoke runner можно, отдельно маркируя непроведённые runtime checks.

## Блокеры и риски

- Официальные README и пакет задач отсутствуют; фактический формат импорта неизвестен. Подзадачи `A3-01b` и `A3-01e` блокируются до получения материалов.
- Docker Engine установлен на хосте как бинарный пакет, но не активен; доступность daemon/rootless runtime не подтверждена. `A3-01d` пока `NOT_RUN`.
- Отсутствие Engine не разрешает запускать participant code вне изоляции и не позволяет записать pass для `J01/J03/T18`.

## Передача следующему агенту

Продолжить в этой feature-ветке реализацией минимального Docker smoke runner без утверждений о непроведённом запуске. После получения доступа к daemon выполнить реальный bounded smoke test; после получения official package прочитать README и проверить одну задачу на настоящие OK/WA. Затем отдельно перейти к `A3-02`. Результаты существуют только в `feature/sandbox-proof`, не в `develop`.
