## Цель и основание

По прямому поручению команды подготовить выпуск GitFlow `0.1.0` в `main`. Репозиторий требует `release/0.1.0` от develop → PR в main → annotated `v0.1.0` на merge commit → обратный PR/merge в develop. Поручение выпуска дано приёмочным документом как допустимый путь; оно не заменяет acceptance gates.

- Версия Python уже `0.1.0`; frontend `package.json` и lockfile синхронизируются на `0.1.0`.
- Добавляется release note с возможностями, quick start и чёткими лимитами acceptance.
- Обновляются README, ROADMAP и интегрированный STATE как coordinator, без изменения acceptance-статусов.
- Evidence: Docker worker реально вернул OK/WA и публичный snapshot не включал private data. Это не подтверждает M0 целиком: CE/TL/ML/RE, автоматический winner advance, hostile/restart и official package остаются открытыми.

## Проверки и ограничения

- На момент подготовки Docker CLI/daemon доступны, но `.env` отсутствует; приватный runtime не запускался этой задачей и секреты не создавались.
- Release PR CI будет единственной обязательной широкой проверкой exact release head: все пять jobs должны пройти.
- Release не объявляется полным MVP/case acceptance. Статусы M0/M1/M2 и T01–T21 остаются PARTIAL/NOT_ACCEPTED согласно ROADMAP/evidence.

## Очистка веток

До удаления обновить refs и подтвердить PR/ancestor статусы. Удалению подлежат только remote `feature/*`, доказанно вошедшие в origin/develop и не связанные с открытым PR; сохранить origin/main, origin/develop, origin/develop-P1 и все refs, чьи коммиты ещё не вошли в develop. Локальные ветки активных worktrees не удалять вместе с пользовательскими checkout.

## GitFlow итог

Здесь зафиксирована подготовка, не публикация. Публикационный audit добавляется после PR в main, точного tag ref и подтверждённого back-merge в develop.
