## Результат по кейсу

- `TEAM01`/`S02`: permission layer различает активные роли приложения; привилегированные Django флаги не повышают роль участника.
- `T02`: register/role assignment из A1-02.1 и базовые role permissions проверены; реальных admin write endpoints, tournament permissions и полного сценария inactive account пока нет, поэтому `T02` не закрыт.
- `T20`: role bypass кейсы этого среза проверены unit/integration probes. Object-level IDOR, чужие source/history, CSRF hostile suite и остальные injection/runtime checks не выполнены; `T20` остаётся `NOT_RUN` в целом.
- Объектное владение не реализуется этой подзадачей: `has_object_permission` подтверждает глобальную роль; конкретные ownership checks должны быть заданы endpoint/domain policy в A1-03/A2.

## Риски и следующий шаг

Нет реального admin mutation endpoint, на котором можно подтвердить весь путь запроса; применённые probe views изолируют тест глобальной роли. Не использовать эту работу как доказательство закрытого T02/T20. Продолжить A1-02.3: создать защищённую idempotent management command первого application admin, не передавать пароль в argv/logs и не выдавать Django superuser автоматически.
