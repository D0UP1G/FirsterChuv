## Дефект и исправление

На source #57 `configure_match_run` была обёрнута в `transaction.atomic()` до `_problem_snapshot`; каталог мог выполнить ORM SELECT внутри этой deferred transaction, после чего два first-configure потока пытались перейти к UPDATE. Новый file-backed barrier test воспроизвёл необработанную `django.db.utils.OperationalError: database is locked` на исходной реализации.

Catalog version/checksum теперь разрешаются до открытия короткой transition transaction. Первое ORM действие внутри — write reservation через UPDATE Match; дальнейшие state reads, проверка двух игроков, создание единственного immutable MatchRun и присвоение current_run выполняются в той же транзакции. Это сериализует конкурентные одинаковые configure вызовы без удержания write lock на время catalog provider.

SQLite `BUSY/LOCKED` (по SQLite extended error codes или строго известным lock messages) преобразуется в общий `MatchRuntimeBusy` с `status_code=503` и `code=match_runtime_busy`; SQL детали не передаются. Non-SQLite ошибки не переводятся в contention. `OperationalError` из каталога больше не скрывается общим "problem is not ready" обработчиком; его busy-коды доходят до retryable mapping, прочие ошибки пробрасываются.
