## Выполненные изменения

- Добавлена app `backend.apps.judge` с `LocalJudge`, реализующим общий `JudgeProvider` и `LanguageRegistry` метод `is_supported`. Provider грузит точную пару `problemId/version`, сравнивает checksum и language ID с неизменяемой версией, проверяет только серверный compiler registry и вызывает sandbox для compile и каждого отдельного теста.
- Реальные sandbox statuses переводятся в OK/WA/TL/ML/RE/CE. CE diagnostics ограничены 8 KiB и находятся только во внутреннем `JudgeResult`; expected outputs, source и diagnostics не добавляются в public DTO. Unconfirmed SIGKILL, Docker/database errors и неподдерживаемый task limit дают `JudgeInfrastructureError`, не verdict.
- Python runner размещён в `backend/apps/judge/runner.py`, который входит в API package/image. `sandbox/runner.py` оставлен compatibility import; smoke CLI импортирует canonical backend module. Это учло `backend/Dockerfile`, копирующий только `backend/`, и не потребовало изменения чужого Dockerfile/Compose.
- Docker runner принимает только валидированные task time/memory limits: 1–120 000 ms, 32–512 MiB на test; compile остаётся под фиксированным cap. Test input cap поднят до 8 MiB в соответствии с внутренним archive cap. Каждый test по-прежнему получает отдельный контейнер без сети, host mounts и секретов; процессы, output, wall watchdog и cleanup ограничены.
- `ML` возвращается только после `docker inspect` с точным `.State.OOMKilled=true`; неразъяснённый kill остаётся infrastructure error. Compiler `cpp20` оставлен `verified=False`.
- Добавлены unit/policy tests и gated реальный integration test, который программно импортирует synthetic bundle и компилирует/запускает решение только через настоящий Docker runner. Он не подменяет runtime verdicts и пропускается без явного `FIRSTERCHUV_REAL_JUDGE_SMOKE=1`.
- Новая app зарегистрирована собственным `JudgeConfig` в `backend/config/settings.py`. Миграции, shared API routes, `context/STATE.md`, общие контракты и чужие feature ветки не менялись.

- J02 реализован на уровне общего порта `JudgeProvider.execute(TrustedJudgeJob)`; image/compiler policy не задаётся клиентом.
- J01/J03 покрыты реализацией core и unit/policy checks частично. Реальный Docker compile/run, OOM, hostile isolation и cleanup не подтверждены в этой среде.
- E03 получает отображение verdict внутри provider; async API/worker, история и browser flow находятся в P3-04/P4-04 и не заявляются готовыми.
- Формат официального checker не придуман. `judging.md` требует взять его protocol и code meanings из README пакета, а пакет/README в репозитории отсутствуют; checker job сейчас завершает typed infrastructure error. Побайтное сравнение применимо только к synthetic expected-output case и не заменяет checker для нескольких допустимых ответов.
- Official P01/P02/T12 и полные T14/T18/T20/T21 остаются открытыми. Smoke bundle не выдаётся за официальный пакет.

## Решения и отклонения

- Подтверждённые решения ADR01–ADR04 и вариант Б не изменялись; новый ADR не нужен.
- Checker protocol оставлен fail-closed до official README. `cpp20.verified` не повышался по unit tests или наличию Docker CLI.
- Docker CLI/Engine wiring и запуск worker не добавлялись в Compose/API image: runtime handoffs закрепляют worker/Compose coordination за P3-04.2/P1-04. Текущая конфигурация не предоставляет judge-worker Docker CLI/Engine access.
- Общие contracts, schemas, public DTO и event formats не менялись.

## Блокеры и риски

- Без Docker Engine нельзя подтвердить реальную компиляцию, task time/memory caps, OOM evidence, network/host/secret isolation, image availability и cleanup. До такого proof catalog/compiler gate остаётся `NOT_READY`.
- Production runtime ещё требует trusted worker и Docker CLI/Engine wiring; provider core сам по себе не образует сквозной путь посылки.
- Official package/README отсутствуют, поэтому checker protocol и официальная приёмка заблокированы внешней зависимостью P3-06.
- Это implementation slice; интеграция и case acceptance не закрыты.
