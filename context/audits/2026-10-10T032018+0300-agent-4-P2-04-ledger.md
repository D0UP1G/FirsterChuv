# Agent 4 · P2-04 accepted/result/failure ledger

Дата: 2026-10-10, Europe/Moscow. Feature `feature/a4-p2-04-ledger-persistence`, исходная база `475cdf71fa88de6aa5aad2142fc9fdbdf90625f6`. На момент аудита изменения находятся в локальном worktree и ещё не опубликованы.

## Цель и сверка с кейсом

Срез закрывает persistence часть P2-04 (M05/M07/J04, T09/T10/T19): считать матч по неизменяемому набору задач/правил и accepted/result ledger; ждать уже принятые посылки после deadline; не превращать отказ judge/worker в WA, RE или автоматическое поражение; атомарно завершать score, clock, winner, продвижение и событие. Сверено с ROADMAP v5, runtime-handoffs, M0 G03–G05 и кейсом (стр. 5: одинаковые задачи/правила, явное равенство, ручной запуск и продвижение; стр. 7: задержки/ошибки проверки, повторы, очередь, понятное сообщение и сохранение посылки).

## Реализация

- В собственной feature сохранена ancestry #58 обычным merge commit `011fd77` и required frozen `participant_user_ids` из stacked #59 — вторым ordinary merge `608c116`. Source refs #58/#59 не менялись; чужие ветки не переписывались.
- `register_accepted` и `apply_result` сначала резервируют writer на run, затем читают receipt. На SQLite contention повторяется целая ledger-транзакция ограниченное число раз; исчерпание возвращает `LedgerPersistenceBusy`/503. Accepted PK и per-accepted result обеспечивают повтор без второго эффекта. Сохраняется результат старого run без изменения score нового.
- Добавлены `InfrastructureFailureRecord` и migration `0007`. Sink принимает только common receipt с одним из четырёх кодов, отклоняет receipt для другого run/уже завершённой посылки и безопасно переживает exact retry. Infrastructure failure не записывает `AttemptResult`/verdict; настоящий результат разрешает незавершённую failure запись.
- Deadline переводит run в FINALIZING, drain учитывает все accepted rows. Retryable failure остаётся pending; terminal unresolved failure оставляет run в FINALIZING без winner и без финального settlement event, `resolutionRequired` видно через private match DTO. После реального result финализация продолжается. Финальный score event не дублируется, если его уже опубликовал последний доставленный result.
- `match_api` теперь строит score/task attempts из persistent ledger, а не изменяемого queue status. Frozen participants сверяются с текущими slots. Private DTO добавляет только allowlisted `reasonCode`/`retryable`, `resolutionRequired`; public schema/event не расширялись, source/diagnostics не читаются. Обновлены v1 schema/fixture и архитектурные docs.
