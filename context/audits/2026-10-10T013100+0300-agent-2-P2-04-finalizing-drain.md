## Цель и исходное состояние

Закрыть durable lifecycle после P2-04 accepted/result ledger: по дедлайну остановить admission, оставить run в FINALIZING при неполных verdicts, после drain завершить счёт/победителя и атомарно опубликовать разрешённое событие и продвижение в сетке. Проверены AGENTS.md, Agent 2 карточка, ROADMAP P2-04, runtime/clock/result ledger модели, event service и актуальный head PR #58. До изменения типизированные accepted/result receipts и pure pending-aware `can_finalize` существовали; persistent service не переводил RUNNING в FINALIZING, не закрывал run и не публиковал score events.

## Выполненные изменения

- `backend/apps/competition/ledger_persistence.py`: добавлен `reconcile_match_run_deadline`, который проверяет текущий run и серверное время; на deadline атомарно фиксирует FINALIZING и блокирует дальнейший admission через существующую RUNNING guard. Если pending attempts нет, пересчитывает score, завершает run как FINISHED или TIED, и сохраняет Match status.
- Последний результат в FINALIZING завершает run только если pure ledger сообщает `can_finalize`. Идемпотентный повтор не дублирует score event.
- Победитель записывается как TournamentParticipant и переносится в зарезервированный downstream slot в той же транзакции. В tie победитель не выбирается.
- Добавлен безопасный serializer публичного `score.changed` payload только из user ID/display name, задач/лейблов, счёта и нормализованных verdicts. Событие append и результат/score/state/downstream используют ту же DB transaction. Исходный код, email и diagnostics в public DTO не входят.
- `backend/apps/competition/tests/test_ledger_persistence.py`: проверены exact deadline и граница за миллисекунду, FINALIZING при pending result, completion на последнем receipt, повтор без второго event, no-pending tie и продвижение победителя.
- `context/agents/agent-2.md`: checkpoint переведён в IN_REVIEW с явным описанием остатка.

## Сверка с кейсом

Покрывает durable часть M05/M07 и таймер/result финализацию T09/T10/T19. Не заявляется как end-to-end или полный P2-04: production deadline tick scheduling, trusted queue/result adapter, infrastructure failure recovery и потребители SSE остаются внешними CONNECT/acceptance.

## Решения и отклонения

Использован уже существующий allowlisted event store и атомарный append вместо отдельного outbox: state, score, downstream slot и event находятся в одной транзакционной БД, как допускает ROADMAP. Tie оставляет run TIED и не назначает случайного победителя; отдельная rematch политика видна через status и P2-05 command.

## Блокеры и риски

Deadline reconciler — callable persistence service, но его ещё не вызывает production worker/scheduler; до интеграции run может оставаться RUNNING после прошедшего времени, при этом submission admission уже закрывает exact deadline server clock. Infra failure sink/recovery не добавлялся. PR #58 stacked на #57 → #50; checks для незамёрженной ветки отсутствуют.
