## Цель и исходное состояние

ROADMAP v6 поручает добавить HTTP ready action, автостарт `both_ready` и стабильную идемпотентность команд config/start/ready с привязкой ключа к телу. В `develop` существовало core `mark_match_ready`, но HTTP маршрут отсутствовал; config/start не сохраняли долговечные body-bound receipts. Кейс и требования проверены по `docs/requirements.md`, API и параллельному контракту, а также страницам 5–7 кейса: участники готовы к началу матча, матч стартует после готовности обоих; зрительская конфиденциальность и изоляция исходников сохраняются.

## Выполненные изменения

- Добавлена модель `MatchCommandReceipt`: SHA-256 ключа и запроса, действие, actor/match scope, исходный JSON-ответ и optional run; migration `0008_matchcommandreceipt.py`.
- Добавлен транзакционный command executor: SQLite write reservation перед чтением receipt/state, bounded retries только на SQLite BUSY/LOCKED, точный повтор возвращает сохранённый ответ, повтор ключа с иным действием/телом возвращает 409. Для config catalog snapshot читается вне write transaction и пропускается при точном replay.
- Добавлен CSRF-защищённый `POST /api/v1/matches/{id}/ready`, ограниченный active assigned participants; приватный чужой матч скрывается как 404. `manual` сохраняет ready signal, `both_ready` запускает clock на втором сигнале с server time.
- Config и manual start переведены на те же durable receipts. Идемпотентный ключ ограничен 1–128 печатными UTF-8 байтами.
- Обновлены URL, `docs/architecture/api.md`, `docs/architecture/parallel-contracts.md`, ROADMAP и карточка A4. Изменения в A3-owned apps/config/Compose/CI и A5 frontend не вносились.

## Сверка с кейсом

- Покрывает часть M05 и требования по началу матча: конфигурация/run сохраняют текущий контракт; активные назначенные игроки могут подтвердить готовность; второй сигнал в `both_ready` атомарно переводит матч в running.
- CSRF, actor/match scope, чужой match 404, idempotency conflict и no-store private response проверены. Публичная карта/anonymous access остаются отдельными задачами P1-03/P2-06; сквозной браузерный M0 не заявляется.

## Решения и отклонения

- Сохранён response payload каждого успешного командного запроса, а не только факт выполнения: это делает точный повтор устойчивым даже после последующего изменения состояния матча.
- Config catalog подготовка выполняется до основной транзакции, чтобы сохранить короткую SQLite write transaction; перед retry receipt/state проверяются заново под reservation.
