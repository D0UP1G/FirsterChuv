## Цель и исходное состояние

ROADMAP v3 ставит после fixes P2-02.1 и P2-06.1 задачу persisted match runtime P2-03. Clock arithmetic уже реализован в PR #11 и повторно не менялся. Перед этой сессией feature была основана на `b9c25cb`; после проверки новых refs `origin/develop` оказался на `6320b4b`, и он включён в feature обычным fast-forward без конфликта. На свежем ref проверены карточка agent 2, roadmap, требования M05/M06/P03, v1 match fixture, parallel contracts и runtime handoffs. PR #7 (`feature/bracket-runtime`) остаётся OPEN с `mergeStateStatus=DIRTY`; модели Match/MatchRun ещё не доступны в develop.

## Выполненные изменения

- Добавлен `backend/apps/competition/domain/start_policy.py`: неизменяемое состояние readiness двух участников и чистая команда `mark_player_ready`.
- Поддержаны оба контрактных режима `manual` и `both_ready`. Повтор ready идемпотентен, включая повтор после старта; второй distinct ready запускает clock ровно на серверном времени второго сигнала только в `both_ready`.
- Проверяются состав участников, допустимость ready IDs, режим запуска, состояние запуска, членство actor и timezone-aware серверное время. Новые сигналы не принимаются для WAITING/RUNNING runs.
- Добавлены 7 policy tests в `backend/apps/competition/tests/test_clock.py`; существующие clock tests оставлены в `MatchClockTests`.
- Обновлена карточка `context/agents/agent-2.md` с фактической базой и ссылкой на audit.
- API, ORM, миграции, shared registrations и контракты не менялись. Эта pure policy не является production persistence/runtime provider.

## Сверка с кейсом

Срез поддерживает M06/T08: `manual` сохраняет READY до отдельного старта, `both_ready` запускает по готовности обоих. P2-03, M05/M06 и T07–09 не закрыты полностью: конфигурация матча, immutable task/scoring snapshot, persisted MatchRun lifecycle, gateway/workspace authorizations, API и clock worker/restart остаются открытыми. M05/T07 также требуют setup и состояния задач.

## Решения и отклонения

Сделан только независимый pure policy sub-slice P2-03. Полный persisted runtime нельзя корректно привязать к Match/MatchRun без интеграции PR #7. Не менял чужую ветку, PR или её файлы. Чужие изменения из develop сохранены обычным fast-forward. P2-06.1 опубликована отдельно в PR #16, а не смешана в этой ветке.

## Блокеры и риски

PR #7 остаётся OPEN/DIRTY; его lifecycle/match models являются конкретной зависимостью следующего P2-03 persistence/API шага. Текущий pure gate сам по себе не защищает конкурентные запросы между процессами: persistence service должен вызвать policy и сохранить ready set плюс старт clock атомарно в транзакции.

## Передача следующему агенту

После CI/review этого PR продолжить P2-03 с persisted current MatchRun/config/API на свежем `develop`, как только PR #7 интегрирует модели. До этого P2-03 persistence находится в `WAITING_CONNECT` на конкретные Match/MatchRun schema; по очереди agent 2 можно продолжить с независимым ledger/result core P2-04. Изменения этой сессии находятся только в `feature/match-ready-gate`, не в develop.
