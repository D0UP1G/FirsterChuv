## Цель и исходное состояние

P2-04 требует immutable accepted attempts, идемпотентного result application, защиту от out-of-order и superseded results, ожидание pending результатов перед завершением, а также persistence, technical failure handoff и downstream/event delivery. Pure score #13 уже присутствует в develop; этот slice добавляет ему ledger state без повторения арифметики. На ветке отсутствуют `Match`/`MatchRun` модели: PR #7 на актуальном head `1a2b54a` остаётся OPEN/DIRTY. В `backend/apps/common/contracts.py` пока нет согласованного `InfrastructureFailureReceipt`/`InfrastructureFailureSink`; runtime handoff относит добавление общего порта к P1-02.5/A1.

Перед началом загружен свежий `origin/develop` `56c20eb` (PR #35 MERGED) и включён в feature обычным fast-forward. Изменения PR #35 не затрагивали competition/common ledger или карточку agent 2.

## Выполненные изменения

- Добавлен чистый неизменяемый `ResultLedger` на один frozen run: participant/problem/scoring snapshot и `AttemptReceipt` записи.
- `register_accepted` фиксирует только receipt ожидаемого run; точный duplicate no-op, конфликтующий submission ID отклоняется.
- `apply_result` требует существующую accepted receipt и точное совпадение ID, run, actor, task, серверных времени/elapsed и scoring version.
- Идентичный повторный `ResultReceipt` не применяется повторно; конфликтующий result отклоняется.
- Score пересчитывается по всей записанной истории через существующий pure scoring core, поэтому out-of-order delivery использует authoritative server timeline, а не порядок callback.
- Если переданный persisted current run ID отличается от ledger run, receipt записывается в исторический ledger, `applied=false`, score отсутствует; текущий rematch не меняется.
- Пока у любого accepted attempt нет final result, переход явно возвращает `can_finalize=false`. Заданные verdict enums повторно не расширялись.
- Добавлены 9 ledger tests в существующий `test_scoring.py`, который уже запускается domain suite runner. API, ORM, миграции, common contracts и shared runner не менялись.

## Сверка с кейсом

Этот pure core поддерживает server-authored attempts/results и scoring snapshot по M05/M07/J04; покрывает часть T09/T10. Он не закрывает полную score/winner/finalization acceptance: нет persistent ledger, CompetitionGateway, атомарной транзакции с submission store, технического failure sink/recovery, public event/outbox, winner/downstream promotion. T19 и acceptance технического завершения остаются открытыми.

## Решения и отклонения

Выполнен только независимый pure domain slice; не добавлял самодельный общий failure DTO до слияния аддитивного порта A1. Accepted item без ResultReceipt продолжает блокировать `can_finalize`, что fail-closed до terminal technical-failure/manual-recovery wiring. Не менял общие контракты, чужие ветки, AppConfig, URL или `context/STATE.md`. Результат не использует fake verdict.

## Блокеры и риски

- Durability и concurrent idempotency требуют persistence в transaction; pure immutable state сам по себе не сериализует процессы.
- Technical failure receipt/sink ещё не доступен; до подключения terminal failure остаётся unresolved pending и не может дать автоматического победителя.
- Match/MatchRun schema и winner/downstream transaction ожидают интеграцию #7 и будущий runtime layer.
- P2-03 readiness PR #34 — OPEN/CLEAN на head `730edd8`, четыре CI checks SUCCESS; merge не выполнялся.
