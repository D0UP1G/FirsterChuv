## Выполненные изменения

- Admission полностью повторяется максимум три раза: исходная попытка и не более двух коротких повторов. Для каждого повтора SQLite busy/locked ошибка выходит из `transaction.atomic`, затем откатывается вся попытка; задержки между повторами — 25 и 75 ms.
- Повтор выполняется только для SQLite `SQLITE_BUSY`/`SQLITE_LOCKED` (включая extended result codes) или точных типовых lock messages при отсутствии numeric code. Другие `OperationalError` повторно не выполняются.
- Серверный `accepted_at` вычисляется до цикла и сохраняется между попытками; idempotency lookup также входит в повторяемую admission операцию.
- После исчерпания попыток service поднимает `AdmissionBusy`; API отвечает `503 queue_busy` с инструкцией повторить тот же `Idempotency-Key`. Документация приложения описывает retry и запускает race suite с отдельной file-backed test settings.
- Добавлены forced-lock tests на bounded retry, исходный `received_at`, отказ повтора несвязанных DB ошибок и API 503. File-backed `TransactionTestCase` использует два реальных thread connections и DB-backed test ledger/event ports; покрывает одинаковые/разные ключи, capacity race, rollback submission/counters/ledger/event и отсутствие `OperationalError`/500.
- Добавлены только собственные `backend/apps/submissions/test_settings.py` и тестовый файл; production settings, schemas и shared CI workflow не менялись.

## Сверка с кейсом

Изменение поддерживает J04/T19: при временной SQLite конкуренции уже принятая admission transaction откатывается целиком и повторяется ограниченно; exhausted contention становится явным временным отказом, а не HTTP 500. Повтор клиентом использует прежний Idempotency-Key. Вердикты, worker и sandbox не менялись. Полные T09/T14/T19/T20 не объявляются выполненными: нет production A2 adapters/worker/LocalJudge, browser и hostile integration acceptance.
