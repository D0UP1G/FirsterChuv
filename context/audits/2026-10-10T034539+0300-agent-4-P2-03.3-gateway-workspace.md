## Выполненные изменения

- Добавлен `backend/apps/competition/gateway.py`: `DjangoCompetitionGateway` реализует common CompetitionGatewayV1 и RunProblemSnapshotProvider, плюс factory entrypoints для явного runtime wiring.
- `authorize_submission` проверяет PLAYED match/run связь и current-run identity, frozen participant user ID, активное participant membership/account, принадлежность задачи run snapshot, RUNNING и серверную дату до deadline; elapsed/scoring version возвращаются из run. Подмена actor или match/task/run даёт общий 404; state/deadline conflict — 409.
- `authorize_workspace` возвращает только purpose-scoped actions для metadata/statement/draft/history. Участник допускается только по активному членству и frozen roster; условие скрыто до стартовавшего состояния run. Текущий/исторический draft scope привязан к user/run/task; admin может читать metadata/statement, но не source/draft/history.
- `resolve` возвращает `problemVersion`/SHA-256 checksum исключительно из `MatchRun.problem_versions`; умеет разрешать superseded run для уже принятой очереди и не опрашивает latest catalog. Повреждённый worker snapshot даёт типизированный runtime error; API access maps повреждённое состояние в 503.
- Gateway делегирует accepted/result/infrastructure-failure receipts в проверенный durable ledger и возвращает `ResultApplication` для идемпотентной доставки.
- Добавлены 9 сценариев `backend/apps/competition/tests/test_gateway.py` и документация provider в `backend/apps/competition/README.md`. Обновлены API docs, Agent 4 card, roadmap/STATE и отдельный merge audit P2-04.

## Решения и отклонения

Соблюдён common v1 без изменения contracts. Statement до старта возвращает пустую capability set участнику; global admin сохраняет текущую policy из `match_api` и может читать statement, но не draft/source. Accepted/result/failure persistence переиспользует уже integrated P2-04 service вместо второго ledger.
