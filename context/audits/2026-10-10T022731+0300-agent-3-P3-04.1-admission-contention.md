## Цель и исходное состояние

ROADMAP v5 назначил P3-04.1 для устранения фактической SQLite lock-ошибки в конкурентном same-key admission из первого CI-запуска PR #63. Ошибка возникала на `QueueCounter.objects.get_or_create(scope_key=key)` как `database table is locked: submissions_queuecounter`; успешный повтор CI не считался исправлением. Существующий сервис уже повторял целую admission transaction до трёх раз только при SQLite `BUSY/LOCKED`, но одинаковые интервалы повтора могли синхронизировать потоки.

До исходников изучены root/Agent 3 инструкции, PROJECT/STATE, ROADMAP v5, требования и кейс, architecture/parallel contracts, GitFlow, runtime handoffs, M0 acceptance и последние релевантные аудиты. Карточка Agent 3 помечена `IN_PROGRESS` до изменения исходников. Рабочий каталог изолирован в managed worktree; общий checkout и сторонние worktree не менялись. Ветка синхронизирована с #67 обычным merge `origin/develop`; сам `develop` не менялся.

## Выполненные изменения

- `backend/apps/submissions/services.py`: перед повторным idempotency read внутри admission transaction добавлена write-first операция `QueueCounter.objects.bulk_create([QueueCounter(scope_key="global")], ignore_conflicts=True)`. Она обходит read-before-write `get_or_create` на общем contention point и сериализует admission writers; дальнейшая проверка idempotency, capacity, submission, accepted receipt и event остаётся в той же транзакции. Существующая обработка retryable SQLite locks и преобразование исчерпанного повтора в `AdmissionBusy` не ослаблены.
- `backend/apps/submissions/tests/test_admission_concurrency.py`: same-key сценарий синхронизирует оба потока непосредственно перед их первым write-intent; проверяет один вызов результата на обоих потоках, один submission/accepted receipt/event, исходное время получения и единственный резерв capacity.
- `context/agents/agent-3.md`: карточка обновлена фактической базой/merge, изменёнными путями, результатами, статусом и следующим шагом.
- `context/audits/2026-10-10T022731+0300-agent-3-P3-04.1-admission-contention.md`: этот audit.
- Миграции, API DTO, общие контракты и `context/STATE.md` не менялись.

## Решения и отклонения

Вместо увеличения количества или длительности повторов исправлен порядок работы с contention point: admission транзакция первой выполняет запись, затем читает idempotency и резервирует capacity. Никакие произвольные DB ошибки retryable не объявляются. В `docs/architecture/decisions.md` новое архитектурное решение не требуется: публичная граница и алгоритм очереди не изменены.
