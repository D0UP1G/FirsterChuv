# Контекст проекта

Обновлено: 2026-10-09, Europe/Moscow.

## Цель

FirsterChuv создаётся для хакатонного кейса «Платформа соревнований по спортивному программированию». Нужно провести блиц-турнир 1×1 на выбывание, дать участнику условия и редактор на странице матча, реально проверить код и показать зрителю ход борьбы.

Источник: PDF «Кейс_Платформа_соревнований.pdf», 8 страниц, [включён в репозиторий](../docs/source/Кейс_Платформа_соревнований.pdf). SHA-256: `8d0d0a843b00ac4d35845fabf02963f793ee3115870fa5f3b108176f809bd008`. Матрица требований со страницами источника находится в `docs/requirements.md`. Официальный пакет задач пока не получен.

## Подтверждено командой

- Работа строго по GitFlow.
- Роль хранится у аккаунта глобально: `participant` или `admin`.
- Новый аккаунт автоматически становится участником и не может создавать турниры.
- Администратор создаёт и редактирует турниры, назначает участников и управляет соревнованием.
- Зритель может быть не зарегистрирован. Публичный просмотр не требует роли аккаунта.
- Нужны общая папка контекста, отдельный аудит каждого агента, документация архитектуры и роадмап агентов. Первоначально четыре роли; 2026-10-10 команда поручила создать отдельного frontend owner A5 и перераспределить остальных по ROADMAP v4.
- Сейчас приоритет: минимальный работающий MVP по кейсу.
- Стек: Django REST Framework + React, SQLite3.
- Реальные вердикты выдаёт собственная песочница: вариант Б кейса.
- Яндекс Контест нужен только для возможности импортировать задачи; внешняя проверка через него не используется.
- Безопасность и защита от инъекций обязательно отражаются в архитектуре, задачах и приёмке.

Ранее обсуждалась одна универсальная учётная запись с правами на уровне турнира. Команда заменила это решение на глобальные роли. Не возвращаться к старой модели без новой инструкции команды.

## Границы MVP

Обязательные блоки 1–3 кейса: управление турниром, условия задач, редактор и реальная проверка. В командный MVP также включена базовая зрительская карта, живая сетка и проекторный режим, поскольку визуализация даёт до 15 баллов.

Первый работающий срез показывает весь путь от приглашения до вердикта и продвижения победителя. Он ещё не считается полным MVP по кейсу, пока не завершены обязательные функции управления и обработки сбоев. Все функции помечены в матрице требований и роадмапе.

Не входят в MVP: двойное выбывание, группы, матчи на 3+ человек, Telegram/e-mail уведомления, отдельная система рейтинга, реплей с перемоткой, комментаторская панель, показ чужого кода, плагиат и контроль переключения вкладок.

## Предлагаемые детали реализации

- TypeScript, Monaco, SSE и Docker Compose поверх подтверждённого стека.
- Сохраняемая в SQLite очередь и один judge-worker в MVP; Redis/Celery не обязательны.
- Docker как компонент изоляции: отдельный ограниченный контейнер на запуск, компиляция также внутри изоляции.
- Глобальный `admin` управляет всеми турнирами в MVP. Ограничение «только свои турниры» можно добавить отдельным решением, если команда его потребует.

Статусы этих решений и порядок перехода на другой вариант: `docs/architecture/decisions.md`.

## Внешние зависимости и неизвестное

- Официальный пакет задач и его README не получены агентом. Формат импорта нельзя считать известным.
- Для импорта из Яндекс Контеста не подтверждены доступные методы, форматы и права; не считать, что API отдаёт закрытые тесты, чекеры и эталонные решения.
- Для выбранного варианта Б не требуется создавать Яндекс-соревнование или иметь права `contest:submit` / `contest:manage` для официальной проверки. Требования конкретного импортера нужно выяснить отдельно.
- Срок хакатона, состав команды и ресурсы demo-хоста пока не зафиксированы.

Приоритет следующей работы: получить пакет и доказать реальную проверку одной задачи в изоляции. Макет UI или тестовый mock не заменяет это доказательство.
